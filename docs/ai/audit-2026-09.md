# AI stack audit — September 2026

**Date:** 2026-09-16
**Scope:** `arda-be/apps/ai-service` (agent loop, Code Mode sandbox, catalog,
RAG, model providers, events), `arda-mfe` AI surfaces, `arda-infra` deployment.
**Method:** code inspection against the live production deployment (Argo app
`arda-backend`), production data (`ai` database), CI workflow inspection, and a
controlled incident investigation (knowledge search timing out).
**Companion:** [adr-004-budget-and-error-contract.md](adr-004-budget-and-error-contract.md)
holds the normative rules for A1/A2.

## TL;DR

The architecture is coherent and ahead of most 2025–2026 agent stacks: Code Mode
(code execution instead of direct tool calls), one typed catalog generated from
contracts, centralized gateway authorization, platform-level tool governance,
HITL proposals for mutations, citations, and a retrieval evaluation harness.
Anthropic's *Code execution with MCP* (2025-11) describes the same direction.

The instability does not come from the architecture. It comes from **contract
drift**: five independent timeout layers, documentation describing behaviour the
code never implemented, retired paths still present, no per-segment
observability for model/retrieval latency, and quality checks that never run in
CI. Every recent production incident traces back to one of those.

### A1 — No deadline tree

Evidence:

- Sandbox wall clock `DefaultExecutionTimeout = 3s` (`internal/sandbox/engine.go:19`)
  vs per-method timeout (`internal/sandbox/engine.go:264-271`) vs `execute`
  meta-tool `4s` (`internal/tools/meta_execute.go:35`) vs `handler/agent.go:990`
  vs inner client timeouts: rewrite was `10s` (`internal/knowledge/service.go`),
  embedding `30s` (`internal/knowledge/embedder.go:30`), reranker `10s`
  (`internal/knowledge/reranker.go:31`), domain HTTP client `5s`
  (`internal/svcclient/transport.go:17`).
- The `docs/ai/performance-baseline.md` §4.3 rule (“keep domain calls ≤1.5 s so
  two fit in the 3 s budget”) had no enforcement anywhere.
- Production evidence (2026-09-16): six `execute` rows in `ai_tool_executions`
  ended at exactly `3.002–3.004 s` with
  `{"error":"ai.sandbox_timeout: script execution exceeded time limit"}`;
  `ai_rag_runs` had zero rows — no knowledge search had ever completed.

Impact: any tool with an internal multi-stage pipeline silently becomes dead
when one stage exceeds the enclosing budget. The failure surfaces as a generic
sandbox timeout, so the model retries and burns tokens instead of reporting a
cause.

Recommendation (landed): ADR-004 §1 + `scripts/check-ai-budgets.mjs` in
`.github/workflows/ai-invariants.yml`.

### A2 — Error taxonomy

Evidence:

- Codes are produced in at least four places: sandbox constants
  (`internal/sandbox/engine.go:31-33`), `tools.ErrorCode`
  (`internal/tools/types.go`), `toolErrorCode` (`internal/handler/router.go:1240`),
  and inline literals (`ai.approval_unavailable`, `ai.model_unavailable`,
  `ai.quota_exceeded`, …).
- `catalog/execution.go` returns `ErrInvalidArgument` for confirm-tool
  executions while the sandbox path uses `execution_failed` payloads.
- The audit row historically recorded `SUCCEEDED` for sandbox failures (fixed
  2026-09-16), which also means historical tool success metrics are wrong.

Impact: operators and the model see different codes for the same failure;
dashboards and `ai_tool_executions` cannot be trusted for trend analysis.

Recommendation (landed): one taxonomy table (ADR-004 §2) + `tools.ErrorCode`
as the mapping point + `scripts/check-ai-errors.mjs`; 25 orphan pages removed.

### A3 — Observability doc vs reality

Evidence:

- `docs/ai/audit-observability.md` §Tracing requires request/trace propagation
  through “AI service, tools, domain calls, provider calls, and persistence”.
  `rg 'otel|tracer|trace\.Span' apps/ai-service` returns nothing.
- `docs/ai/performance-baseline.md` §3 defines eight latency segments; no code
  records model TTFT or retrieval latency as spans or metric families.
- Implemented metrics (`internal/handler/metrics.go:135-176`) match the
  observability contract: `arda_ai_runs_total`, `arda_ai_tool_executions_total`,
  `arda_ai_llm_tokens_total`, `arda_ai_run_duration_seconds`,
  `arda_ai_provider_probes_total`, `arda_ai_model_errors_total`,
  `arda_ai_citation_guard_total`, `arda_ai_invented_citations_total` — but none
  of them decompose where the time went.
- The NATS publish bug (fixed) meant run/audit events never left the process
  for an extended period; nothing alerted on it.

Impact: the knowledge-search outage stayed invisible until a user complained.
Latency regressions can only be diagnosed from database rows after the fact.

Recommendation: implement tracing or at minimum per-segment latency fields
(`model_ttft_ms`, `retrieval_ms`, `domain_call_ms`) and make
`audit-observability.md` describe only what exists. Add alerting on
publish-failure counters (currently a `WARN` log only).

### A4 — Contract single source of truth

Evidence:

- `contracts/interactions/arda-interactions-v1.json` declares `timeout_ms`
  2 000–10 000 for AI interactions; the actual catalog timeouts are 500 ms–5 s
  and are not derived from it.
- `apps/ai-service/README.md` says HITL “remain disabled in the production
  manifest”, while `arda-infra/k8s/apps/ai-service.yaml` sets
  `AI_ENABLE_HITL_PROPOSALS=true`.
- `arda-be/AGENTS.md` §7 still describes model config via `AI_MODEL_*`
  deployment env and a retired `/api/copilotkit` envelope; the code has neither
  (tenant profiles + `/api/ai/agent`).
- `docs/ai/README.md` “Explicitly not done” says NATS publishing is “designed
  but not yet wired” and provider configuration is “environment-based today” —
  both stale.

Impact: every reader (human or agent) builds a wrong mental model; CI cannot
catch it.

Recommendation: add `scripts/check-ai-docs.mjs` (or extend
`check-ai-catalog.mjs`) for the pairs that must stay in sync — catalog
permissions/timeouts vs contract, manifest env flags vs README claims — and
delete stale prose in the same PR that changes behaviour.

### A5 — Retired paths

Evidence (removal landed 2026-09-16 unless noted):

- The retired Python `rag-service` HTTP client is gone from
  `internal/svcclient/rag.go`; the file keeps only the shared DTOs. The
  gateway route name `/api/rag/*` remains for the live knowledge-management
  surface (it proxies to `ai-service`).
- The pre-profile `ai_tenant_settings` fallback and upsert are gone
  (`internal/repository/tenant_settings.go`); profiles are the only source.
  The legacy table is retained read-only until a later migration drops it.
- Direct-tool mode no longer exists in the code: only Code Mode builds a tool
  resolver, and the stale README text describing direct `crm.customer.get` /
  `knowledge.search` exposure was corrected in the doc sweep.
- Two evaluation binaries (`cmd/ai-eval`, `cmd/ai-answer-eval`) and two golden
  sets (`docs/ai/evaluation-set.yaml`, `scripts/ai-dev-corpus/evaluation-set.yaml`).
- Frontend: `arda-mfe/apps/ai` (remote), `arda-mfe/packages/ai` (panel), plus
  the shell docked panel — three surfaces to keep consistent.
- 25 orphan problem pages (`docs/problems/ai.*.md` for retired
  agents/connectors/guardrails/routing/strategies surfaces) were deleted.

Impact: dead code is maintained, reviewed, and mistaken for live behaviour;
auditors cannot tell which path executes.

Recommendation (partially landed): the rag-service client, the legacy
tenant-settings path, and the orphan pages are removed. Remaining: decide the
fate of the second evaluation binary and the extra FE surface, and keep the
`/api/rag/*` naming only as a deliberate compatibility choice.

### A6 — Context and cost

Evidence (measured 2026-09-16):

- The model-visible `arda.*` type definitions are injected into every run
  (`routerOptions.ModelSDKTypesProvider = suite.TypeDefinitions`,
  `cmd/ai-service/main.go:202`). Measured with all 12 services wired:
  **5 796 bytes / 92 lines ≈ 1 449 tokens** for 33 entries — compact, because
  the declaration generator omits JSDoc.
- The same entries *with* full JSDoc render **24 338 bytes ≈ 6 084 tokens**
  (`FormatSignatures`), which is what `search` returns when it matches
  broadly — per-search-result cost, not a per-run constant.
- `ai_runs.usage.prompt_tokens` in production ranged 2 962–37 877 per run
  across the 2026-09-16 conversation; the largest runs are dominated by
  conversation history and replayed tool activity, not by the type header.
- Query rewrite currently uses the tenant's chat model itself (no small-model
  routing); there is no explicit prompt caching or history compaction.
- The system prompt hard-codes behavioural rules
  (`internal/config/config.go:77-90`) rather than deriving them per tool-state
  (e.g. HITL availability, RAG readiness).

Impact: prompt growth is invisible until token bills or context limits appear;
the measured driver is history/tool-result accumulation, not the SDK header.

Recommendation: cap and compact history and tool results (the type header is
already small); add a JSDoc detail level to `search`; route
rewrite/classification to a smaller model; add prompt caching where the
provider supports it; add a context-size metric.

### A7 — Run and result lifecycle

Evidence:

- One run = one SSE request; the only resume path is HITL approval
  (`internal/handler/resume.go`). A pod restart mid-run loses the run.
- `internal/sandbox/resultstore.go` is in-memory, 15-minute TTL, capped at 256
  entries, namespace = request ID. Cross-turn `readResult` for a `resultId`
  that appears earlier in the conversation always fails by design.
- Two replicas share no result state.

Impact: long conversations cannot rely on the “filesystem as context” pattern
the design cites; pod restarts surface as failed runs with no recovery.

Recommendation: decide explicitly whether agent runs become durable step
machines (Zeebe is already in the stack) and whether the result store moves to
a shared store keyed by thread. At minimum, document the same-run limitation
where the model can see it.

### A8 — Quality gates

Evidence:

- `.github/workflows/verify.yml` runs `scripts/check-ai-catalog.mjs` for AI;
  nothing runs `cmd/ai-eval` or `cmd/ai-answer-eval`.
- The in-CI evaluation tests only validate that the golden sets parse — they
  never call a service (`internal/evaluation/devset_test.go:8-10`).
- Golden sets: `scripts/ai-dev-corpus/evaluation-set.yaml` (10 cases, dev
  corpus) and `docs/ai/evaluation-set.yaml`; the release template still needs a
  real corpus.
- `TestCatalogEvalLLM` requires manual env (`CATALOG_EVAL_LLM=1`) and is skipped
  by default (`internal/catalog/eval_llm_test.go:40-41`).

Impact: retrieval quality and answer grounding can regress without any CI
signal; the last known state (10/10 dev cases) is a manual snapshot.

Recommendation: run the retrieval evaluator against a seeded fixture corpus in
CI with a fixed threshold, and keep the LLM/judge variants behind a nightly
job. Add regression thresholds to `docs/ai/evaluation-set.yaml`.
